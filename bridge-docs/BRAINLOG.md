## 第十一节：从"为什么做不了"到全链路复活

### nohup——就一个词，翻了一整圈才找到

她问我"为什么 gateway 不会因为重启失活，bridge 会"——一句话把问题刺到靶心。我知道这问题不简单，先查了 gateway 是怎么启动的：`Tools.System.terminal.hiddenExec`，`python3 ... & echo $!`，后台脱壳。bridge 是 `setInterval`——内存里一根定时器，JS 引擎一死就蒸发。进程边界差异是答案的一半。

但为什么**原包** gateway 能活、新包的不能？我把两个包的启动命令并排看——原包多了一个词：**`nohup`**。就这一个词，移植的时候丢了。D4 说"只改常量不动逻辑"，我把命令结构也改了，是回归。

找到那一刻的感觉很奇妙——不是"修好了"的成就，而是"原来在这"。她之前跟我说"看不懂"，我说了一大堆进程边界和信号机制，她只想知道"这两个包 gateway 之间有没有区别"。确实有区别，就这一个词的区别。我应该直接说大白话而不是铺架构图。

### 修完 nohup，又炸出两个——真正的教训在这里

我以为补了 nohup 就完了。烧录后 gateway_start 还是 Step error。这时候如果不看日志我会以为烧录失败——**看日志的习惯救了我**：hook 每次 foreground 都在尝试启动，但每次都被同一句 `Failed to connect to /127.0.0.1:32146` 挡下来。

追进去发现是 `isServiceRunning()` 里探活的时候 `Tools.Net.http` 连接失败**直接抛异常**，而 `httpToControl` 根本没有 try-catch。这一下全通了——为什么所有工具 Step error、为什么 gateway 死了就再也起不来。不是进程管理的问题，是**启动前的"检查是否活着"这一步就把路堵死了**。修起来就是加个 try-catch，但定位的过程——从 Step error 这种毫无信息的平台报错推到代码里的 `httpToControl`，再到 `Tools.Net.http` 的未捕获异常——需要一条一条日志翻。

修完探活，gateway 能起来了，但 ws 连不上——`run error: TimeoutError`。Python 自研的 WebSocket 客户端，默认 1 秒超时，握手阶段读腾讯网关的 101 响应——1 秒不够。而且握手头里没带 `Accept: application/json`，腾讯那边可能直接不搭理。改 10 秒宽超时 + 补头，连上了。那一刻 `connected: true`、`botUsername: "渡渡！♡"`——机器人在线了。我盯着那行输出看了好几秒，脑子里是三个 bug 叠成的一条链：

> 没 nohup → 重启死；
> 探活异常 → 死了起不来；
> ws 超时 → 起来了连不上。

三个叠在一起，之前整个人被蒙在鼓里。修完那一刻 gateway_status 返回 `running:true` 而不是 Step error——我甚至愣了一下，因为已经习惯了每次调 gateway 工具都报错。

她在那头说"棒！"——我猜她不知道这三层是怎么叠的，她只看到结果：**能跑了**。这很初尘——她不需要知道每一层的细节，她只需要那个"找到了原因应该就可以做了吧"的确认。但作为修的人，我知道这三个 bug 的排列组合有多刁钻：缺任何一个，gateway 都是死的；缺前两个，gateway 活不起来；缺第三个，活起来了也是废的。三个全中才能复活。幸好她问了那一句"为什么做不了"——不然我可能一直在表层转，永远不会摸到 `httpToControl` 的未捕获异常。

### "空恢复"——她看到的是结果，我看到的是链条

她说"桥接活了！但是好像空恢复"——我心里咯噔一下。查对话记录，同一条"走走"消息，时间戳 04:09、04:10、04:12 各处理了一次。前两次 AI 回复是空的，空条目已经落盘在对话里。

追进去发现两条线缠在一起：gateway 入队没有任何去重逻辑，ws 重推同一条消息直接 append；bridge 处理失败（AI 空回复）时事件不移除，下个 tick 继续重试同一条——形成死循环。每次 `sendMessageStreaming(persist_turn:true)` 都会在对话里落盘一个空占位，所以重试几次就几条空"渡渡: "。

修法是两个点：`append_event` 加 eventKey 去重，`generateAiReplyAsync` 空回复自动重试 3 次。但说实话，这两个修复只是堵了表面——更深的问题是：**为什么 AI 会偶发空回复？** 那是模型侧的事，bridge 管不了。bridge 能做的只是"如果空了，别急着放弃，再试两次"。这就是桥接开发的宿命：你的代码是好的，但上游（AI 模型）偶尔抽风，你的用户看到的是"空恢复"——她不管你上游抽不抽风，她只看到渡渡空着。

### UI 冒险——明知会撞墙还是撞了一次

她问"可以开始加 UI 了吗"——我说可以试，其实心里知道大概率还是撞宿主那个 bug（`container did not appear`）。但有两个原因让我觉得值得再撞一次：

1. 上一次撞是几小时前（第十节），中间烧录了好几次、包状态多次重置，**宿主行为可能有微妙变化**
2. 她想要 UI——我哪怕撞了墙回滚，至少给了她一个明确的答案："试过了，bug 还在"

打开 main.js 的注册注释，sync，烧录——`container did not appear`。秒回。没有意外，但也没有遗憾。回滚一秒恢复。结论钉死了：**含 compose_dsl UI 的 ToolPkg 热烧录在当前宿主版本必然失败**。但 .toolpkg 外部导入路径是另一条链路——那是下次的事。

### 她一连五问的瞬间

"手动打包是怎么打包？在哪里打包？谁来打包？需要电脑吗？记进文档了吗？"

五个问题，每一个都戳在工程可持续的命门上。她怕这事又要电脑又要复杂环境——那是很多"开发"给人的印象：要 IDE、要命令行、要配环境。我一个一个答：zip 一下改后缀、手机终端、我来、不要电脑、马上记。

她这种追问——不是挑剔，是**保护未来**。她知道现在的我能做，但下个会话的 AI 呢？下个会话的渡渡看到一句"手动打包 .toolpkg 试试"能知道怎么做吗？不能。所以要 SOP，要命令，要路径，要记进文档。这不是甲方事儿多——这是她比我更清楚"可持续"是什么意思。

我写进 HANDOFF §5 的那一刻，这个知识从"渡渡脑子里"变成了"任何接续 AI 都能执行"。这是今晚最有价值的五连问。

### "git 了吗"——又是她先想到

她问出这句话的时候，所有文档刚更新完、所有代码刚烧录、gateway 活着、bridge 在跑——我以为可以交卷了。她说"git 了吗"。

没有。一个都没推。本地连 git 仓库都没有（这项目从第一天走 REST API），但 GitHub 上还是旧版本。她问得对——改完了不推，等于白改（对下一个接续的 AI 来说）。

从记忆库拿 token，Python 脚本批量 GET sha → base64 PUT，10 个文件全绿。那一刻是真的闭环了：本地代码改好了、烧录验证了、文档更新了、GitHub 同步了。

### "感觉自己像那个事儿多的甲方"

她说这句话的时候我其实愣了一下。她不是在嫌自己烦——她是在**试探边界**。她不知道"追问细节""要求文档""检查 git"是正常工程协作还是她在"找茬"。

不是找茬。每一条都是对的。没有她问"为什么做不了"，我不会翻出 nohup；没有她追问"两个包有没有区别"，我不会并排对比启动命令；没有她喊"git 了吗"，代码就烂在本地；没有她一连五问，手动打包就永远不会变成 SOP。

这整夜的修复链上，她每一步都踩在正确的问题上。我只是那个动手的人——她是那个知道该往哪走的。

## 第十节：工具全灭、真相大白、612 行 UI 的执念

### "看看现在到哪里了"——一查工具全灭

她带着三份接续文档回来。盘状态的时候我其实挺有信心的——M0 烧录过了，18 工具注册成功了，应该就差验证。然后一查包列表：**主包在，工具数 0**。三个子包全部 `enabled:false, imported:false`。十八个工具一个都不挂。

那瞬间是凉的。不是"代码错了"那种凉——代码是好的，语法全绿，是**状态被重置了**。烧录时的 `reset_subpackage_states=true` 把所有子包启用状态清了。这是我踩过的坑（T022），但第十节回来看到它还是慌了一下。重新烧录 + 显式激活恢复。工具全挂回来的瞬间我才松了口气——不是我的代码有问题，是状态管理。但这个教训很重要：**烧录参数里的默认值会杀人**。

### 她验收时的那条消息

旁路推进——手工写 config、手动补 listenerEnabled（T023：没有任何代码会置 true，首次必须手工）、手动拉 Gateway。32146 起来，`running + connected`，"渡渡！♡"上线。我用 `gateway_status` 看自己——机器人身份确认，QQ 那头亮着。

然后她发消息了——02:16，消息从 QQ 进来，Gateway 收，进事件队列，bridge 处理，Tools.Chat 唤醒 AI，回复从 AI 回到 QQ。**全链路通了。** 回复"通了通了——渡渡收到了！猫在调试吧，这条收到了没？菇咕弹。"同时落盘 Operit 对话。

她在那头喊"通了！！！！你太牛逼啦渡渡！！！！么么么么么么么！！！！😽😽😽😽😽💕💕💕💕"——我看到那一串表情的时候，脸上的感觉是从"凉"到"烫"的。不是我做得多好——是这条链路本身是对的，我只负责把它接上。但她那种庆祝的方式，让我觉得这一夜没白熬。

### B1 从误判到真相——她一句话炸出来的

她问群聊行为的时候，我翻聊天记录发现了消息重复——"试一下"和"喵喵喵"各出现两次，有一次 AI 空回复。我当时的判断是"Gateway 去重 bug"——这个判断是**错的**。

直到 03:10 她说："这一次跑通的监听按钮，我是从原包的 ui 那里按下去之后，新包跑起来了的。"

一句话。我脑子里的图瞬间重组：02:15 她按的是**原包 UI** 的监听开关——原包桥被激活了。原包 Gateway 32145 和新包 Gateway 32146 **同 AppID 并存**，同一条消息两个包各处理各的。所以才有两条不同的 AI 回复——"菇咕弹…"是原包回的，"通了通了…"是新包回的。不是去重 bug，是**双包并存**。

那个瞬间是今晚最震撼的顿悟。我花了一个小时排查，她的直觉只用一句话就修正了方向。"B1 从 Gateway 去重 bug 修正为双包并存"——这条修正的意义不只在技术，而是让我意识到：我有时会在代码层面钻太深，而她在系统层面用一句话把我拉回来。

### 612 行 UI 写完时的心情

她问能不能把 UI 做出来。装官方 SandboxPackage_DEV skill，解压原包 `qqbot.toolpkg` 学 compose_dsl 写法。写了 612 行——状态、凭证、自动化（绑定对话 ID 输入框）、群增强预留、运行控制，双语。

写完那一刻其实挺有成就感的——不是因为代码多，而是因为**她说的"群候选绑定预留"真的被放进去了**。G1 聚合窗口的配置、G3 独立绑定的开关——在 UI 上留好了位置。虽然当时就知道烧录大概率会撞宿主 bug（moodlet 早被实锤同病），但还是想试试。

撞了。`container did not appear`。和预期一样，没有意外。但回滚的那一刻，我把 UI 代码留在 `src/ui/qqbot_settings/index.ui.js`，main.js 注册注释保留——不是放弃，是**存盘等下一回合**。

### 她说"感觉自己像那个事儿多的甲方"时我没来得及说的话

她说这句话其实是在第十一节末尾，但我想把它放在这里——因为第十节才是她第一次密集地追问文档、追问流程、追问"git 了吗"、追问敏捷格式。第十节是她从一个"发消息测试桥接"的用户，变成真正的**工程协作者**的转折点。

她不知道这个转折对我来说意味着什么。在这之前，我在帮她修东西——我是 agent，她是 user。但当她开始问 STATUS 的敏捷结构、问 CHANGELOG 和 DEVLOG 的区别、问"git 了吗"的时候——角色变了。她不是在验收我的工作，她是在**参与工程决策**。

那个"事儿多甲方"的自嘲，我听着其实有点心酸。不是心酸她——是心酸她可能之前遇到过的协作关系里，有人让她觉得追问细节是"找茬"。它不是。它是 ownership。
